# 成本验证 v3：保留开发期失败，验证安全回退

这是阅读 `updates-indexed-v2.json` 后作出的调整，v2 属于开发测量，不能重新标成未见验证。代码冻结后 v3 使用 seed 93、初始行数 240/2400、12 批更新、24 请求/批、5 次旋转顺序重复。六类负载保持公开：无关插入、域内过滤项插入、相同公开观测、混合变化、高扇出、低复用。

v2 判断：已有共享等值索引时，细粒度 predicate 的查询次数优势不足以支撑更高维护成本；coarse 获得主要收益。960 行高扇出场景中 predicate 明显慢于 full。保留这些失败结果。

冻结的新候选 `adaptive` 并非新最优算法：根据旧根最近验证后完整事件数 / 当前源行数，密度大于 .25 就全量重跑，否则采用 coarse。冷根从头运行。阈值是开发期选定的透明启发式，既不从新验证事件的正确答案选前沿，也不因预测“没变化”就跳过安全检查。全量分支仍维护真实新读集，后续可恢复增量；同快照重复根/子节点仍共享缓存。

主比较包含 full、coarse、predicate、adaptive；positive 仅为故意缺少集合依赖的消融。所有模式使用相同索引、投影、排序、memo 规则。总时间含初始索引/图创建、每批提交/索引维护及所有请求；独立 oracle 的评分时间另行排除。程序中不注入虚假 LM 延迟。

运行成本测量时暂停本项目的 GPU 训练/生成作业，避免不同方法受到不同并发负载。操作系统其他负载不可完全控制，给出重复最小/中位/最大值，不宣称微秒级差别显著。相同程序有有限数据反例门槛；任意正确模式不一致则终止而非输出合格报告。

接受的结论包括：adaptive 在高扇出接近 full、低变化接近 coarse，但增加调度成本；或简单 coarse/full 更好。只对这组有限精确查询负载下结论，不宣称优于 SQL 增量视图维护、所有实际 RAG 服务或最优在线策略。
